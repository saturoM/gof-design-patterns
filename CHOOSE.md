# Як обрати патерн (анкета)

Правило: спочатку знайди **симптом**. Назва патерна — в кінці, не на початку.
Якщо після питань лишається «і так зійде без патерна» — **без патерна**.

---

## Крок 0 — де болить? (30 секунд)

Прочитай свій код уголос і вибери одне:

- А) «Щоб змінити *що створюється*, я правля `new` / `if` у **багатьох** місцях» → Creational  
- Б) «Два модулі **не стикуються** за інтерфейсом, або треба обгортка/дерево частин» → Structural  
- В) «Розростається `switch`/`if` за **поведінкою**, статусом або алгоритмом» → Behavioral  

Немає А/Б/В — патерн швидше не потрібен.

---

## Creational — діагностика

### Симптом A1
У кількох сервісах один і той самий «глобальний» обʼєкт (логер, клиент метрик), і ти боїшся що хтось зробить другий.

Питай далі:
- Це має жити **лише в памʼяті одного процесу**?  
- У тесті тобі **потрібно підмінити** його на фейк?

| Відповіді | Висновок |
|---|---|
| Так, процес; підміна важлива | Не класичний Singleton — **один інстанс через DI** |
| Так, процес; підміна не важлива | Singleton / module singleton — ок для інфри |
| Має бути спільним між кількома api / після рестарту | Це **не** Singleton → БД / Redis (SoT) |

### Симптом A2
Зʼявляються гілки `if (type) new X; else new Y` у контролері або use-case, і новий `type` змушує правити **це місце + ще кілька**.

Питай:
- Різниця між X і Y — саме **різні класи/політики створення**?  
- Клієнту достатньо знати спільний інтерфейс?

| Так / так | **Factory Method** (або проста factory-функція — почни з неї) |
| Ні, просто багато полів одного класу | Не FM → дивись Builder (A3) |

### Симптом A3
Конструктор роздутий: FX, fees, defaults, optional-поля; виклики `new Invoice(...)` з 8+ аргументами або з «магічними» дефолтами розкидані по коду.

Питай:
- Порядок збірки важливий / є проміжні кроки?  
- Хочеш заборонити «напівзібраний» інвойс?

| Так | **Builder** (або dedicate `CreateInvoice` service — теж ок) |
| Ні, лише вибір класу за type | Повернись до Factory Method |

### Симптом A4
Треба одразу пачка **сумісних** речей: «якщо mock-rail, то й mock-fx і mock-webhook signer»; «якщо live — інший набір». Мішати mock+live небезпечно.

Питай:
- Обʼєкти мають народжуватись **сімʼєю**, не по одному?
- Клієнт не повинен знати конкретні класи членів сімʼї?

| Так / так | **Abstract Factory** |
| Ні, лише один обʼєкт різного типу | Factory Method досить |

### Симптом A5
Створення з нуля дороге (важка ініціалізація), а новий обʼєкт майже як існуючий.

| Так | **Prototype** (клон + підкрутка) |
| Ні | Не Prototype |

---

## Розведення сусідів (часті плутанини)

| Плутанина | Питання-розвідник |
|---|---|
| Singleton vs «один рядок у БД» | Переживе рестарт і другий інстанс api? → БД |
| Factory Method vs Builder | Болить *який клас* чи *як зібрати поля*? |
| Factory Method vs Abstract Factory | Один продукт чи **набір сумісних** продуктів? |
| Builder vs просто конструктор | Чи є незаконні проміжні стани без Builder? |

---

## Structural / Behavioral

Заповнимо після відповідних тижнів тим самим стилем: симптом → уточнюючі питання → висновок.

---

## Міні-правило

1. Знайди симптом.  
2. Відповіси на 1–2 уточнення.  
3. Візьми найпростіше рішення, що знімає біль.  
4. Імʼя GoF — лише ярлик для розмови й коміту.
