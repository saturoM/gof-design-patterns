# Creational — плюси / мінуси / питання-підвід

Полиця: **як створити**. Правило: спочатку питання до болю, потім імʼя патерна.

---

## 1. Singleton

**Питання-підвід**
- Чи потрібен **рівно один** екземпляр **на цей процес**, і всім — той самий?
- Це інфра (логер/конфиг процесу), а не бізнес-сутність (Invoice)?
- Чи має правда переживати рестарт і кілька інстансів api? → якщо так, це **БД/SoT**, не Singleton.

| + | − |
|---|---|
| Одна точка доступу до спільного ресурсу процесу | Схоже на глобальну змінну |
| Просто для логера/метрик «на процес» | Важко мокати / підмінити в тестах |
| | Один на процес ≠ один на весь світ |

У Nest часто краще **DI (один інстанс)**, ніж ручний `getInstance()`.

---

## 2. Factory Method

**Питання-підвід**
- Чи розʼїхались `if (type) new X else new Y` по коду?
- Клиєнту досить **спільного типу**, а конкретний клас вирішує творець?
- Чи додавання нового виду змушує правити багато місць із `new`?

| + | − |
|---|---|
| Легко додати новий тип в одному місці | Зайвий шар, якщо тип завжди один |
| Клиєнт не залежить від concrete class | Можна переускладнити просту фабрику-функцію |

Приклад PSP: «створи on-ramp **або** off-ramp інвойс».

---

## 3. Abstract Factory

**Питання-підвід**
- Чи треба одразу **набір** речей з **однієї теми** (mock/live, UA/US, юрисдикція)?
- Чи небезпечно змішати частини різних тем?
- Чи зміна середовища = підміна **однієї** фабрики?

| + | − |
|---|---|
| Важко змішати несумісне | Багато інтерфейсів/класів |
| Тема міняється в одному місці | Новий член сімʼї → правки всіх фабрик |
| | Overkill, якщо в сімʼї один продукт → FM |

Приклад PSP: mock **або** live стек (rail + FX + signer).

---

## 4. Builder

**Питання-підвід**
- Конструктор роздутий (багато аргументів / магічні дефолти)?
- Чи є **незакончений** стан, який не можна віддавати клієнту до кінця?
- Збираємо **один** складний обʼєкт, а не сімʼю незалежних сервісів?

| + | − |
|---|---|
| Кроки замість монстр-конструктора | Overkill для 2–3 простих полів |
| `build()` = момент «готово» | Більше коду (builder + steps) |

Приклад PSP: invoice amount → FX → fees → create.

---

## 5. Prototype

**Питання-підвід**
- Чи є хороший **донор/шаблон**?
- Новий обʼєкт ≈ старий, різниця мала?
- Чи збірка з нуля дорожча за клон + підкрутку?

| + | − |
|---|---|
| Швидко; менше дублювання логіки збірки | Потрібен акуратний deep copy |
| Зручно «як той, але…» | Поганий шаблон розмножує помилки |

Приклад PSP: дублікат шаблонного інвойса + новий amount.

---

## Шпаргалка вибору (Creational)

| Якщо чуєш… | Патерн |
|---|---|
| один на процес (інфра) | Singleton / DI-singleton |
| який **тип** створити | Factory Method |
| **комплект** однієї теми | Abstract Factory |
| з нуля **по кроках** один складний | Builder |
| є **шаблон**, мала різниця | Prototype |

Сусіди: FM vs AF = один vs сімʼя · Builder vs Prototype = з нуля vs клон · Singleton vs SoT = процес vs світ.
